<h2>一、误区一：把榜单位置当成线路质量的替代指标</h2>
<p>榜单本身不生产数据，它只是把某一时刻的报价和文案重新排列。同一家供应商在不同榜单上名次能差十几位，差别通常来自合作方式而不是网络表现。把名次当成质量信号，等于把别人的商务关系当成自己的技术评估。</p>
<h3>先看榜单是怎么排出来的</h3>
<p>翻到页面底部找"排序说明"，多数写的是"综合评分"或"编辑推荐"，没有权重、没有采样时间、没有样本量。三个要素缺一个，这个排序就无法复现。可复现的评估至少要说明测了哪些节点、什么时段测的、样本多少、失败怎么计。</p>
<h3>把名次换算成三个可查字段</h3>
<p>与其记名次，不如记三条硬信息：出口 ASN 归谁、地址被情报库打成什么类型、单地址允许几个并发会话。前两条用 whois 和公开 IP 库交叉查，第三条只能问。三条对上了，名次高低就不重要了。</p>

<h2>二、误区二：一次 ping 就给整条线路定性</h2>
<p>ICMP 往返只能说明链路通不通，说明不了 API 调用顺不顺。Claude 的接口走 TLS，握手、首字节、长连接复用各有一段开销，这些在 ping 里全看不见。更麻烦的是单次测量的偶然性：一次 140ms 可能只是恰好赶上了空闲时段。</p>

<h3>分时段取中位数和 P95</h3>
<p>在 10:00、20:00、23:00 各跑一轮，每轮 100 个包，看中位数和 95 分位。命令用 <code>mtr -rwzc 100 -i 0.5 目标地址</code>，重点读 Avg、Best、Worst 和丢包率四列。中位数可接受、P95 不夸张，才算稳定；只看最小值容易被运气骗过去。</p>
<h3>用 curl 的时序字段替代体感</h3>
<p>带代理发一次真实请求，让 curl 把各段耗时打出来：<code>curl -x http://用户:密码@网关:端口 -o /dev/null -s -w "%{http_code} %{time_connect} %{time_appconnect} %{time_starttransfer} %{time_total}\n" https://api.anthropic.com/v1/models</code>。握手超过 400ms、首字节超过 1s，日常调用就会明显排队。</p>

<h2>三、误区三：把节点数量读成可用节点数量</h2>
<p>"覆盖 200 个国家、百万级 IP"这类描述说的是资源池规模，不是你能拿到的可用出口。池子再大，分到你账号上的那几条如果集中在同一个 C 段、同一个上游，实际冗余度接近零。</p>
<h3>抽样二十条再算可用率</h3>
<p>让供应商给出十条以上候选地址，用脚本并发探测，记录成功、超时、返回 403 的比例。可用率低于九成的池子，做重试设计的成本会明显上升，因为你要为不确定的失败预留额外请求预算。</p>
<h3>看地区分布的集中度</h3>
<p>把候选地址的 ASN 统计一遍，如果八成集中在两三个 ASN，说明它其实是少数上游转售，地区标签只是地理库里的归属地，不代表线路真的分散。集中度高的池子，一次上游故障就会整片掉线。</p>

<h2>四、误区四：忽略出口复用率这个隐藏变量</h2>
<p>复用率指的是一条出口地址在同一时间被多少个会话、多少个账号共用。它不在任何宣传页上，却直接决定接口调用的失败率。复用率高的地址，请求特征会互相叠加，平台侧看到的是一团混杂行为。</p>
<h3>间接估算复用率</h3>
<p>同一地址在不同时段连续请求，观察响应头的服务端标识、TLS 证书链、以及出口的 TCP 时间戳特征是否稳定。若同一地址在几分钟内出现明显不同的网络特征，基本可以判定被多人共用。</p>
<h3>把并发上限写进合同</h3>
<p>口头说"独享"没有约束力。要求写明单地址并发连接数、超出后的处置方式（限速还是排队）、以及被判定异常时的替换责任。这三条比月费更能决定长期体验。</p>

<h2>五、三个十分钟内能跑完的自查动作</h2>
<p>不必等完整的评估报告，拿到候选地址当天就能做完三件事，先把明显不合格的筛掉，剩下的再进入长周期观察。</p>
<h3>动作一：类型与归属交叉核验</h3>
<p>用 <code>whois -h whois.cymru.com " -v 地址"</code> 查 ASN，再去两三个公开 IP 情报站比对类型标签。三处结果一致才算通过，出现 hosting、proxy 标签直接排除。</p>
<h3>动作二：连续挂机看掉线</h3>
<p>用长连接跑满 6 小时，每 30 秒发一次轻量请求，记录失败时刻。掉线若集中在晚高峰，多半是上游带宽争抢；若随机分布，则更像线路本身质量问题。两类问题的处理方式完全不同。</p>
<h3>动作三：并发压测找拐点</h3>
<p>从 5 并发起步，每次加 5，直到错误率超过 5%，记录此刻的并发数。这个拐点就是你在这条出口上能安全承载的上限，比供应商报的数字更可信。</p>

<h2>常见问答</h2>
<h3>榜单真的一点参考价值都没有吗？</h3>
<p>答：有价值，但只能当线索用。它帮你快速收集一批候选供应商名字，省去漫无目的搜索的时间；至于质量排序、适用场景、售后水平，还得自己按上面的口径测。把榜单当目录，不要当结论。</p>
<h3>复用率低的地址一定不会出问题吗？</h3>
<p>答：不能保证。复用率只是影响出口行为一致性的一个变量，地址历史滥用记录、请求频率、账号本身的状态同样参与判定。低复用率能减少一类干扰，但替代不了整体的环境管理。</p>
<h3>压测会不会把接口额度耗掉？</h3>
<p>答：会占用配额，所以压测要分层做。先用轻量接口或返回极小的请求探路，确认链路稳定后再用真实业务请求小样本验证。压测前把并发上限和配额余量算清楚，别在月中把额度打空。</p>
<h3>延迟达标了，为什么调用还是慢？</h3>
<p>答：慢可能不在链路上。常见原因有三类：连接池太小导致请求排队、没有复用长连接每次重新握手、以及重试策略把一次失败放大成多次串行等待。先用 curl 时序排除链路因素，再回头查客户端配置。</p>
